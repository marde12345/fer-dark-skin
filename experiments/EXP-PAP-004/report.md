## Implementation note: ArcFace embedding path was fixed to avoid re-detection

An earlier version of `tools/papuan_v2/run_ai_predictions.py` reused
`tools/extract_arcface_embeddings.py`'s `ArcFaceEmbedder`, which re-runs
InsightFace's own face **detector** on the already-cropped pilot image
solely to obtain 5-point landmarks for `face_align.norm_crop`. That
re-detection failed to find exactly one face on 50/150 (33%) of pilot
images (48 `excluded_no_face`, 2 `excluded_multiple_faces`) — an artifact
of redundant detection on a tight crop, not a real signal about ArcFace+LR's
usefulness as an annotation assistant. **That 100/150 result was never used
in any agreement computation** and is preserved only as a debugging note
(`superseded_result` in `metadata.json`, and in `docs/EXPERIMENT.md`
EXP-PAP-003).

Fix: Candidate B now calls the recognition sub-model directly
(`insightface.model_zoo.get_model(".../w600k_r50.onnx")` → `ArcFaceONNX.
get_feat()`), which InsightFace's own source confirms does not require
detection or landmarks — it operates on the crop image as given, resizing
internally via `cv2.dnn.blobFromImages`. No detection model is even loaded
for this path (`FaceAnalysis` normally asserts one must be), so a second
detection is structurally impossible here, not just avoided by convention.
The resulting embedding is L2-normalized identically to InsightFace's own
`Face.normed_embedding` before being passed to the same trained
`LogisticRegression` classifier.

**Caveat, stated explicitly (not hidden):** the classifier was trained on
embeddings produced through the full detect+landmark-align pipeline
(`tools/extract_arcface_embeddings.py`). This direct `get_feat()` path
skips that alignment step, relying instead on the crop already being
face-centered by `FaceDetector`'s 20%-padded bounding box. This is a
distributional difference from the classifier's training input and should
be weighed alongside the agreement metrics once they are computed — it is
a different kind of caveat than the selection-bias problem it replaces, not
a guarantee of better accuracy.

## What is NOT complete, and why

**Human labeling of the 150-image pilot set has not been performed.**

I (the assistant implementing this pilot workflow) cannot fill in
`human_labels.csv` — doing so would fabricate the "independent human ground
truth" that the entire pilot design depends on, and would silently defeat
the circularity/independence safeguards the approved proposal specifically
required (`docs/proposal/PAPUAN_V2_RECON_AND_PROPOSAL.md` §11 "Circularity
risk"). A model or script producing its own comparison ground truth is
exactly the self-confirmation-bias failure mode this pilot exists to guard
against.

`tools/papuan_v2/pilot_agreement_report.py` enforces this: it refuses to run
if any row in `human_labels.csv` has a blank `gt_label` (verified — running
it against the current template raises `RuntimeError: ... has 150 row(s)
with an empty gt_label ... Human labeling must be complete and independent
before agreement analysis can run.`).

## What remains to produce the real EXP-PAP-004 report

1. A human annotator opens each of the 150 images in
   `data/papuan_v2/pilot/images/` (filenames match `image_id` in
   `human_labels.csv`) and records a label in `human_labels.csv`'s
   `gt_label` column, ideally without having seen either candidate's
   predictions in `ai_predictions.csv` first (blind labeling preserves the
   independence guarantee).
2. Run:
   ```bash
   uv run python tools/papuan_v2/pilot_agreement_report.py
   ```
   This reads the now-complete `human_labels.csv` and the existing
   `ai_predictions.csv`, and writes `agreement_metrics.json`,
   `confusion_matrices/*.csv`, and overwrites this `report.md` with the real
   per-model accuracy/macro-F1/Cohen's kappa/confusion matrix/confidence-vs-
   correctness results.
3. A human (you, or your supervisor) reviews the report and writes the
   EXP-PAP-004 selection decision into `docs/EXPERIMENT.md` — the script
   does not auto-select a winner.

No code changes are needed for step 2 — the pipeline is complete and tested
(see `tests/test_pilot_agreement_metrics.py`,
`tests/test_pilot_independence.py`); it is only waiting on real human input.
