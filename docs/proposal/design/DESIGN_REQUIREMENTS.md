# Design Requirements

> **Purpose**: Derive design/research requirements from the current problem architecture (`docs/proposal/research/PROBLEM_ARCHITECTURE.md`), the literature-supported gaps (`docs/proposal/research/STATE_OF_ART_AND_GAP.md`), and the candidate RQs (`docs/proposal/research/RQ_OPTIONS.md`), scoped to the current **working direction only** — Structure A+B (FER performance/systematic error characterization as primary, performance/error patterns across measured skin-tone categories as secondary). **Structure A+B is not an official final RQ** and is not silently converted into one anywhere below. No artifact and no methodology is defined here. Requirements are derived top-down (Problem → Evidence → Research Need → RQ Candidate → Requirement), never bottom-up from the fact that ArcFace+Logistic-Regression code already exists in `tools/`.

---

## 1. Requirement Definition — Terms Used

Per `docs/proposal/guideline/PROPOSAL_GUIDELINE_EXTRACTION.md` §12 (BAB 10):

- **Problem**: the gap between current and desired state (already established, `PROBLEM_ARCHITECTURE.md`).
- **Requirement**: what the artifact/design *must do or satisfy* to help close that gap — stated solution-neutrally where possible (guideline p.157: "the system must use machine learning" is normally a design decision, not a requirement, unless genuinely mandated).
- **Feature**: a specific capability a particular implementation happens to have — not itself a requirement.
- **Design decision**: a choice made among multiple ways to satisfy a requirement (e.g., *which* face-representation model, *which* classifier) — made later, in Phase 6 (Artifact Architecture), not here.
- **Objective**: the condition/outcome the *research activity* aims to achieve (already partially derived per-RQ-candidate in `RQ_OPTIONS.md` §7) — requirements support an objective, they are not the objective itself.

Every requirement below is checked against this distinction: if a line item describes *how* something is done rather than *what* must be true of the design, it is rejected or rewritten.

## 4. A+B-Specific Requirements — Detailed Justification

### Performance Evaluation

- **Reproducible evaluation on a clearly defined population** (F-01, D-04): required — without this, no comparison across time, model, or subgroup is meaningful. Not optional under any RQ variant.
- **Controlled baseline comparison** (F-02): required — "systematic error" is only a meaningful phrase relative to a specific, named system's actual behavior.
- **Accuracy**: justified as a **MUST** — it is the minimum summary statistic needed to state whether a classifier's predictions are usable at all, and is already the anchor metric throughout R1–R9.
- **Macro precision / macro recall / macro F1**: justified as a **SHOULD**, not an automatic MUST — they matter specifically because this dataset has known class imbalance (Neutral=76 of 135 vs. Fear=7), so accuracy alone could mask per-class failure; but they are not mandatory for every possible A+B-scoped analysis (e.g., a purely descriptive error-taxonomy sub-study could proceed without them). Justification, not blanket inclusion.
- **Per-class performance where sample size permits**: justified as a **MUST** where D-02's exclusion criteria are satisfied (i.e., for Neutral/Happy/Sad/Surprise/Fear), and explicitly **not required or claimable** for Angry/Disgust given D-02.

### Error Characterization

- **Confusion analysis / class-specific error patterns**: **MUST** — this is the direct operationalization of RQ-1/RQ-3's core question and is not separable from them.
- **Neutral-specific analysis**: **MUST**, specifically because Neutral is both the largest class (N=76 of 135) and the class carrying the strongest existing evidenced pattern (Neutral→Angry) — not required generically for every class at the same depth.
- **Confidence/probability analysis**: **COULD** — existing evidence (e.g., `reports/assets/confidence_histogram.png`, `confidence_per_class.png`) shows this has been explored before, but no current RQ candidate specifically depends on it; including it would need its own justification if pursued further, not automatic inclusion here.
- **Distinction between observed pattern and causal explanation** (A-02): **MUST** — a standing integrity requirement (see §2 above), not RQ-specific.

### Skin-Tone Analysis

- **Explicitly defined skin-tone measurement**: **MUST** — without a defined, documented measurement procedure, "skin-tone category" is not falsifiable or auditable.
- **`Unknown` category handling** (D-03): **MUST** — directly required given the current data's large `Unknown` bucket (N=57/135); silently dropping this requirement would misrepresent the analyzable population.
- **Subgroup sample-size reporting** (A-03): **MUST** — required given how small the current subgroups already are (N=46/N=32); omitting N would make any stratified metric uninterpretable.
- **Stratified performance reporting**: **MUST**, if skin-tone is retained as the working direction's secondary dimension at all — this is the minimum operationalization of RQ-2/RQ-3.
- **Appropriate statistical analysis** (E-02): **SHOULD** — strengthens the finding considerably (as Fisher's exact already did in R7) but a purely descriptive stratified report without a formal test could still have some value at an earlier research stage; escalated to MUST once the finding is intended as thesis-central evidence, per E-02's own wording.
- **Non-causal interpretation** (A-02, X-02): **MUST**.
- **Explicit separation between skin tone and ethnicity** (X-02): **MUST**.
- **A fairness metric (e.g., demographic parity, equalized odds) is explicitly NOT included as a requirement** — no current RQ candidate (`RQ_OPTIONS.md`) frames the working direction as a fairness study, and the dataset's lack of an ethnicity field would make most standard fairness metrics inapplicable or misleading if forced. If a future RQ explicitly adopts a fairness framing, this would need to be revisited and separately justified — it is not assumed here.

## 7. Reproducibility Requirements

- **Fixed model versions**: any classifier or representation model used must have its version/checkpoint identity documented (already practiced for HSEmotion — `enet_b0_8_best_vgaf` — and the existing ArcFace instance — `buffalo_l`/`w600k_r50`).
- **Fixed preprocessing**: face-detection and cropping parameters must be documented and held constant within a single reported comparison.
- **Fixed class definitions**: the 5-class scope (D-02) must be stated explicitly wherever a per-class or aggregate metric is reported, not left implicit.
- **Fixed evaluation population**: D-04's requirement — population identity/size must accompany every metric.
- **Explicit random seed**: R-03.
- **Documented split strategy**: R-02.
- **Explicit exclusion criteria**: R-01, D-02, D-03.
- **Denominator preservation**: D-04, restated here as a reproducibility (not just an evidentiary-honesty) requirement — a third party must be able to reconstruct exactly which N a reported percentage is drawn from.
- **Reproducible reports**: outputs should be regenerable from source data + documented parameters, not manually assembled — already the existing practice (`tools/*.py` scripts, not manual spreadsheet editing).

All of the above are stated as requirements because they are necessary for any future research activity under Structure A+B to produce credible, checkable results — **not** because the existing R1–R9 scripts already do this (though they do; that is supporting evidence, not the justification itself, per the phase's explicit instruction not to justify requirements solely by "the code already does this").

## 11. Preliminary Design Hypothesis

Stated abstractly enough to admit multiple possible implementations — **not a final artifact definition**, and not assumed to be final wording:

> A possible research design, consistent with the current Structure A+B working direction, would need to be capable of: (1) producing reproducible per-sample expression predictions from a named, existing baseline FER classifier on a clearly defined evaluation population; (2) characterizing that classifier's systematic, class-specific error patterns, with explicit attention to whichever class(es) carry the strongest evidenced pattern; (3) stratifying those same performance and error observations across measured skin-tone categories, with explicit, non-imputed handling of an `Unknown` measurement category and explicit sample-size reporting per subgroup; (4) distinguishing observed statistical association from causal or demographic (ethnicity/race) explanation at every point such a stratified result is reported; and (5) doing all of the above in a way that is reproducible from documented data, parameters, and exclusion criteria, and that reports null/negative findings with the same visibility as positive ones.

This description does not name ArcFace, Logistic Regression, or any specific technology — a design satisfying it could be built entirely around the existing HSEmotion baseline with no representation-based comparison at all, **or** could additionally incorporate a representation-based approach (as one candidate mechanism among others) if Phase 6 later justifies that choice against alternatives.

## 12. Design Constraints, Risks, and Assumptions

Kept explicitly separate, per instruction:

### Constraints (external, limiting conditions — not chosen, must be worked within)

- Current dataset size: N=227 historical faces total; N=135 usable common-evaluation subset after exclusions.
- Class scarcity: Angry=1, Disgust=2 ground-truth samples, confirmed at every population stage (227/144/138) — structurally excludes a defensible 7-class evaluation.
- Skin-tone subgroup size: Dark N=46, Medium-Dark N=32 (of N=135) — small, uneven.
- `Unknown` skin-tone category: N=57 of 135 — nearly 42% of the common-evaluation population has no usable skin-tone measurement.
- No ethnicity field exists anywhere in the dataset.
- No person-identity metadata exists — temporal-block grouping is the best available leakage-prevention proxy, not a true identity-based grouping.
- Provenance information for the source film is limited to its title (*Pesta Babi*) — no documented consent/licensing status.
- Available computational resources: not separately documented in this repository beyond what is implied by the already-completed R5–R9 work (local execution, `uv`-managed Python environment, InsightFace/HSEmotion/MediaPipe models already downloaded and runnable) — no formal compute budget or constraint statement exists.

### Risks (uncertain events that could affect the research if they occur)

- A future skin-tone-stratified finding, computed on a still-small sample, may not replicate at a larger scale (already flagged as an open question in `STATE_OF_ART_AND_GAP.md` §5, Gap G2's "what remains unknown").
- Data-provenance/consent issues (X-01), if surfaced later, could constrain what claims the thesis is permitted to make about the dataset, or could require additional institutional review not yet initiated.
- If a representation-based comparison (RQ-4-adjacent) is added later, the compounding of small skin-tone subgroups with the existing 5-class scope could produce cells too small for any defensible per-cell claim (already flagged in `RQ_OPTIONS.md` §3 for RQ-4).

### Assumptions (conditions presumed true, not yet independently verified, that the current working direction depends on)

- That the existing manual ground-truth labels (`data/1408-1010-intermediate/manual_labels_export.csv`) are of adequate quality/consistency for the analyses above — this has not been independently re-audited as part of this phase.
- That the LAB-luminance-derived skin-tone measurement is a stable, consistent proxy across the dataset's lighting/frame conditions — assumed based on its prior use (R7/R8), not re-verified here.
- That temporal-block grouping (`frame_index // 3`) is an adequate, if imperfect, proxy for person-identity in leakage prevention — an explicitly acknowledged approximation (R-02), not a verified equivalence.
